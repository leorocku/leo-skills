# 把内容写成 Obsidian 笔记

## 这个技能在做什么

把用户提供的内容（粘贴的文本、一段对话、一个文件、一个链接）改写成一篇结构清楚的 Obsidian 笔记，写进 vault 里合适的文件夹，打上标签，需要时再配一张 canvas 图。

判断笔记好坏的标准不是"总结得全不全"，而是**三个月后翻到这篇，能不能快速看懂当时在讲什么**。所以宁可写短、写具体，也不要为了覆盖所有细节而写成一锅粥。

## 开始之前先确认两件事

1. **内容是什么** —— 用户想沉淀的是哪段材料。如果用户说的是「把上面的内容整理一下」，就用当前对话里已经出现的那部分，不要凭空扩写。
2. **写到哪个文件夹** —— 见下一节。

如果内容本身太单薄（比如只有一句话），先问用户要不要补充，不要硬凑成一篇笔记。

## 确定写入位置

用户明确说了文件夹，就用用户说的，不要自作主张改。

用户没说时，**推断一个再确认**：

```bash
obsidian folders
```

拿 vault 里真实存在的文件夹列表去匹配内容主题（比如讲 Docker 的命令 → `操作系统/Docker`，讲某个 npm 包的行为 → `全栈/npm`）。然后把推断结果和理由摆给用户看：

> 内容讲的是 Docker 网络模式，我打算写到 `操作系统/Docker/`，可以吗？

用户确认后才写入。**不要静默猜测，也不要因为懒得问就丢到根目录。**

写入前先拿 `obsidian folders` 的输出核对一遍目标文件夹确实存在。

**`obsidian create` 会自动创建不存在的多级目录**（实测确认）。这听着方便，但真正的含义是：路径写错一个字母不会报错，而是安静地在 vault 里造一个垃圾文件夹。所以"核对文件夹存在"这一步不能省——推断出来的位置必须能在 `obsidian folders` 的输出里找到，找不到就说明推错了。

## 选择后端

优先用官方 CLI，它是主线：

```bash
command -v obsidian
```

- **有 `obsidian` 命令** → 用 CLI（下面的流程都按 CLI 写）。
- **没有 CLI，但接入了 Obsidian MCP** → 用 MCP 的对应工具（读文件、写文件、列标签），语义和下面的步骤一一对应。
- **两个都没有** → 停下来说明情况，让用户装 CLI 或配置 MCP，不要改用"直接往磁盘写文件"的方式绕过去。

**CLI 需要 Obsidian 处于打开状态。** 所以动手前先做一次健康检查：

```bash
obsidian files total
```

如果这条命令报错或没有输出，说明 Obsidian 没开或 CLI 没启用。此时**停下来告诉用户「请先打开 Obsidian，然后我再继续」，不要写任何文件**，也不要自己去找 vault 的磁盘路径来绕过 CLI。用户明确选择过这个行为，别用兜底写入破坏它。

**查命令用法用 `obsidian help <命令>`，不要用 `obsidian <命令> --help`。** CLI 不把 `--help` 当帮助开关，`create --help` 会被当成一次真正的创建操作，在 vault 根目录留下一个空的 `Untitled.md`（实测中确实产生了这个空文件，而且在预期的输出目录之外，清理时容易漏掉）。

## 定标签

规则很简单：**最多 5 个，扁平，优先复用 vault 里已有的。**

1. 先把现有标签拉出来：

```bash
obsidian tags sort=count counts format=json
```

用 `format=json` 而不是默认的 tsv，好解析。

2. **丢掉所有带 `/` 的标签。** vault 里存在 `AI/ClaudeCode`、`AI/cc-switch` 这类历史遗留的多级标签，它们不符合要求，既不要用也不要照着新建。用户已经明确说过不要 `AI/Skill`、`软件工程/概念` 这种形式——层级交给文件夹去表达，标签只负责跨文件夹的主题。

3. 从剩下的扁平标签里挑真正贴合内容的，**优先复用已有的写法**（vault 里是 `JavaScript` 就写 `JavaScript`，不要写成 `javascript`；是 `AI` 就写 `AI`，不要新造 `人工智能`）。复用能让新笔记和旧笔记自动串起来，这正是标签的价值。

4. 已有的都不合适时，才新建。新建的标签同样必须是扁平的单个词或短词组。

5. 数量控制在 5 个以内。**宁少勿多**——4 个精准的标签比 5 个里塞一个勉强的更有用。标签只放进 frontmatter，不要在正文里再写一遍行内标签。

## 语言风格：平实朴素

用户明确要求过这个风格，认真对待。具体是：

- 直接说事。不写"赋能""闭环""抓手""生态位""心智模型"这类词。
- 能用短句就不用长句。一句话说清一件事。
- 不堆形容词和副词。"非常重要"、"极其强大"这种评价能省就省，让事实自己说话。
- 加粗只留给真正的关键结论，一段最多一处。满屏加粗等于没有加粗。
- 不写"综上所述""值得注意的是""不难发现"这类填充句，直接进入下一件事。
- **保留原文里的具体数字、命令、路径、版本号、报错原文。** 这些是最有价值的部分，不要为了读起来顺畅把它们抽象掉。`npm ERR! code EACCES` 比"出现了权限错误"有用得多。

一个对照：

> ❌ 本文深入探讨了 Docker 的多种网络模式，旨在帮助读者全面理解其底层实现机制与适用场景。
>
> ✅ Docker 有三种网络模式。默认的 bridge 最常用，容器之间靠 IP 通信；host 模式直接共用宿主机网络；none 模式只有 lo 回环。

## 内容适合时配一张 canvas 图

当内容本身是**结构化的**——流程步骤、方案对比、层级分类、系统架构、时间线——就额外生成一张 `.canvas`，并在笔记正文里用 `![[图.canvas]]` 嵌进去。纯线性的叙述、单一概念的解释、纯操作步骤清单，不配图，配了也是噪音。

canvas 里放的是**结构**，不是原文搬运。节点文字要短，能几个字说清就别写一整句。

样式上必须做到明暗主题下都清楚，具体做法见 [references/canvas-style.md](references/canvas-style.md)。核心三条：

1. 颜色只用预设 `"1"`–`"6"`，不要写十六进制。预设色由 Obsidian 按主题解析，暗色和亮色各有一套值，自动适配；十六进制是写死的，在其中一个主题下必然翻车。
2. **不要给文字设颜色，也不要给文字加描边。** 文字继承主题自己的前景色就是最清楚的。描边只加在图形边框上。
3. 需要明确的描边时，用中灰这一档的中间调颜色。它在白底和深底上都有约 4:1 的对比度，两边都看得清。

**用 CLI 写 `.canvas` 时有个必须避开的坑：`content=` 会把 `\n` 变成真正的换行，而 JSON 字符串里不允许出现裸换行。** `create` 照样返回 `Created:`、退出码是 0，但生成的是一个 Obsidian 打不开的坏文件——失败了却看起来像成功。

所以 canvas 的 JSON 里所有换行都要写成 `\u000A`，它会被原样保留，解析出来仍然是换行。（实测：同一个 JSON 用 `\n` 写进去，`json.load` 报 `Invalid control character`；换成 `\u000A` 后正常解析。这个坑只影响 canvas，Markdown 正文照旧用 `\n`。）

## 写入

**先查重**，不要覆盖用户已有的笔记：

```bash
obsidian file path="目标文件夹/笔记名.md"
```

这一步不能省，因为**重名时 `create` 不会报错，而是安静地生成一个 `名字 1.md`**（实测确认：连续两次写入 `dup_test.md`，第二次得到 `dup_test 1.md`）。你以为写好了，实际上 vault 里多了一篇几乎一样的笔记，这种重复往往几个月后才发现。查重的成本是一行命令，漏查的代价是一篇幽灵笔记。

如果已经存在同名文件，停下来告诉用户，让用户选：取消 / 换个名字 / 换个位置 / 确认覆盖。**得到明确答复前不要加 `overwrite`。**

然后再写入。标题、标签和正文一起通过 `content=` 传，多行用 `\n`：

```bash
obsidian create path="操作系统/Docker/Docker网络模式.md" content="---\ntags:\n  - docker\n  - 网络\n---\n\n# Docker 网络模式\n\n正文……"
```

不用加任何标志：`create` 默认就不打开文件（`open` 是可选参数，不传就不会弹出来）。写完把路径报给用户，用户想看自己会点开。如果用户明确要求写完直接打开，才加上 `open`。凡是没写在 `obsidian help create` 里的参数，都不要依赖。

笔记的基本骨架：

```markdown
---
tags:
  - 标签1
  - 标签2
---

# 标题

一句话说明这篇在讲什么。

## 主体内容
...
```

标题用内容本身的说法，不要写成"关于 XXX 的总结"。

## 写完检查

```bash
obsidian read path="目标文件夹/笔记名.md"
```

确认四件事：文件真的写进去了、frontmatter 的 YAML 没被转义弄坏（检查 `\n` 是否被当成了字面量）、标签数量没超过 5 个、canvas 能正常解析。

**canvas 一定要验。** 把文件读回来用 JSON 解析器过一遍：`nodes`/`edges` 都在、`id` 唯一、每条边的两端都能对上真实节点。这个坑很隐蔽——`create` 会老老实实回一句 `Created:`，但文件可能根本打不开。样式规则（颜色、描边、背景）照着 [references/canvas-style.md](references/canvas-style.md) 末尾的清单再核对一遍。

发现问题就直接改，不要把坏文件留给用户。

## 汇报

写完后简要说明：

- 文件写到了哪里（完整路径）
- 用了哪些标签，其中哪几个是这次新建的
- 有没有配 canvas 图

## 出错时

- **`obsidian` 命令不存在** → 说明 CLI 没装或不在 PATH，给出安装方向，不要换成直接写磁盘。
- **命令报错说连不上** → Obsidian 没开。请用户打开后重试，不要自动重试。
- **`create` 失败** → 把原始报错贴出来，说明可能的阶段（路径非法／文件名含非法字符／权限），给出建议，然后问用户要不要按建议重试。**不要未经允许自动重试。**注意"文件夹不存在"不会是失败原因，因为 `create` 会自己建目录——真出现意料之外的文件夹，多半是路径拼错了。
- 任何情况下都不要删除 vault 里已有的文件，也不要修改用户没让你碰的笔记。
