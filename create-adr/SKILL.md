# create-adr

为当前项目创建一份 ADR（Architecture Decision Record）。ADR 回答的是"为什么这么做"：把决策的背景、理由和被否决的备选方案固定下来，避免后人重复踩坑或推翻决策时丢失上下文。因此内容的准确性比文采重要——宁可写"暂无内容"，也不要编造。

## 工作流程

### 第 1 步：确定编号与文件名

1. **目录**：先检查项目根目录下是否已存在 `doc/adr` 或 `docs/adr` 目录。**查找时不区分大小写**（`Doc/ADR`、`DOCS/adr` 等同样算命中；命中后按目录原名写入，不要重命名它）。找到任意一个就用它，保证全项目只有一个 ADR 目录；若两者同时存在，用 `docs/adr`。都不存在时，创建标准的 `docs/adr`（全小写）再写入。
2. **编号**：扫描目录中形如 `NNN-*.md` 的文件，取最大编号 +1，三位数字补零（如已有 `002-*`，新编号为 `003`）；空目录从 `001` 开始。
3. **文件名**：`NNN-<title>.md`，title 用**简短的英文小写连字符**形式（如 `001-use-postgresql.md`、`003-event-driven-order.md`）。文件名不含日期、版本号和中文；如果用户没给标题，根据决策内容拟一个并向用户确认。

### 第 2 步：收集内容

ADR 由固定的 7 个部分组成，顺序和标题不可更改：

| # | 章节标题 | 要回答的问题 |
| :--- | :--- | :--- |
| 1 | 状态 | 提议中 / 已接受 / 已废弃 / 已替代，四选一 |
| 2 | 背景（Context） | 当前面临什么问题？有哪些约束条件和业务需求？ |
| 3 | 决策（Decision） | 最终选择了什么方案？一句话说清楚 |
| 4 | 理由（Rationale） | 为什么选这个方案？列 3-5 个关键原因 |
| 5 | 后果（Consequences） | 正面和负面影响，包括引入的技术债务 |
| 6 | 备选方案（Alternatives） | 考虑过但没选的方案，以及为什么不选 |
| 7 | 参考（References） | 相关链接、POC 代码仓库、外部文档 |

两种收集模式，根据用户输入的情况选择：

**模式 A：逐项询问**——用户只表达了要创建 ADR、没给细节时使用。按上表顺序一次问一项，问题要具体（例如问理由时提示"可以从团队熟悉度、功能匹配、运维成本、性能几个角度想"）。用户回答"跳过"或表示没有内容时，该节填"暂无内容"，继续下一项。

**模式 B：从输入总结**——用户在提示中已经描述了决策细节时使用。把已有信息归纳进对应章节，**只追问缺失的核心项**（至少要有"决策"和"背景"），其余缺失的章节填"暂无内容"。如果用户输入里只提到了一个备选方案，就只写那一个。

**禁止虚构（两种模式都适用）**：只写用户实际提供或明确隐含的内容。禁止替用户编造他没提过的备选方案、没谈过的理由、不存在的参考资料，也不许臆断状态。凡是没有依据的项，一律填"暂无内容"——ADR 的价值在于忠实记录当时的决策现场，编造的内容比空白更糟糕，因为后来的人会把它当成当时真的权衡过的事实。

无论哪种模式，写文件前把整理好的内容摘要给用户过目一次，确认或补充后再落盘。

### 第 3 步：写入文件

严格使用以下模板，**七个章节标题一个都不能少**，没有内容的章节正文写 `暂无内容`：

```markdown
---
date: YYYY-MM-DD
status: <状态>
---

# ADR-NNN：<决策标题，中文，如"使用 PostgreSQL 作为主数据库">

## 状态
<提议中 / 已接受 / 已废弃 / 已替代>

## 背景（Context）
<问题、约束、业务需求>

## 决策（Decision）
<最终方案，一句话说清>

## 理由（Rationale）
1. **<原因 1>**：<说明>
2. **<原因 2>**：<说明>

## 后果（Consequences）
- ✅ 正面：<...>
- ⚠️ 负面：<...>

## 备选方案（Alternatives）
- **<方案名>**：放弃原因是<...>

## 参考（References）
- <链接 / 仓库路径 / 文档>
```

细节：
- `date` 用当天日期；"状态"为暂无内容时，frontmatter 里省略 `status` 字段。
- **状态怎么定**：从用户语气判断——措辞表明决策已定（如"决定用 X"、"选型定为 X"、"我们换成了 X"）→ "已接受"；还在讨论、提案阶段（如"打算"、"考虑"、"提议"）→ "提议中"；实在确定不了 → 填"提议中"（宁可先按提案记录，等决策敲定后再更新状态）。没有依据时不要写"已接受"。
- 理由、后果、备选方案的列表格式按实际内容增减条目；确实没内容就写"暂无内容"，不要保留空列表。
- **绝不覆盖已有文件**。写入前确认目标编号未被占用，冲突则顺延到下一个空闲编号。

### 第 4 步：收尾

1. 告知用户文件路径和决策的一句话摘要。
2. 按项目文档协作规则补一句提醒（只在相关时说）：
   - 如果决策影响了模块划分、通信方式或部署形态 → 提醒同步更新架构蓝图，并在架构图对应模块下加指向本 ADR 的链接；
   - 如果决策产生了接口/字段层面的规则 → 提醒在对应 Spec 头部写 `遵循 ADR-NNN` 的引用。

## 示例

**示例 1（模式 B）**：用户说"我们把订单服务从同步调用改成事件驱动了，用 Kafka，帮我写个 adr"
→ 已有信息可归纳出决策（Kafka 事件驱动）和部分背景（同步调用慢）。追问理由、备选方案等缺失核心项，生成 `docs/adr/NNN-event-driven-order.md`。

**示例 2（模式 A）**：用户只说"创建一个 adr"
→ 先问"这次要记录什么决策？"，拿到决策主题后按 7 个部分逐项询问，允许跳过。
